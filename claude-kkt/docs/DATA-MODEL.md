# KKT v2 — Data model (PostgreSQL 16, Drizzle ORM)

## Conventions (apply to EVERY table unless stated)

- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`.
- `company_id uuid NOT NULL REFERENCES companies(id)` on every business table (single tenant today, multi-tenant switch later with no migration). Every unique constraint on a business key is **scoped by company_id**.
- `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at timestamptz NOT NULL DEFAULT now()`, `created_by uuid NULL` (staff user id; NULL = system), `version integer NOT NULL DEFAULT 1` on every mutable row — without exception since migration 0005 (the child/engine rows demands, booking_other_charges, rate_card_rates, rate_card_plc_rules, payment_plan_installments, enquiries and lead_follow_ups carry it too; their trigger `bump_version` raises it on every UPDATE that does not set it itself).
- Every foreign-key column has an index whose leading column is that column (migration 0005; `packages/db/test/online.test.ts` fails on any that has none).
- Soft delete for masters & structure: `is_active boolean NOT NULL DEFAULT true`, `deactivated_at timestamptz NULL`. Financial rows are never deleted — status VOID/REVERSED/CANCELLED with reason.
- Money: `bigint` in **paise**, column suffix `_paise`. Percent: `numeric(5,2)`. Area: `numeric(10,2)` sq ft. Business dates: `date`. Event times: `timestamptz`.
- Enums: Postgres enums (`pgEnum`) whose values come from `@kkt/contracts` (UPPER_SNAKE).
- Snapshots and small lists that are always read/written whole: `jsonb` with a Zod schema in contracts.
- Every list endpoint's filter+sort shape has a compound index listed under the table.
- Drizzle schema lives in `packages/db/src/schema/*.ts` (one file per area below), exported from `packages/db/src/schema/index.ts`. Migrations are SQL generated with drizzle-kit and committed.

## A. Identity & platform

**roles** — company_id, name, description, permissions text[] NOT NULL, is_system boolean. UNIQUE(company_id, name).

**users** — company_id, name, email citext, phone, password_hash, role_id → roles, all_projects boolean DEFAULT true, is_active, must_change_password boolean, mfa_enabled boolean, mfa_secret_enc text, mfa_pending_secret_enc text, failed_attempts int DEFAULT 0, locked_until timestamptz, last_login_at, password_changed_at, totp_last_step bigint NULL (last accepted TOTP time step; a code is never accepted twice — migration 0005), avatar_document_id. UNIQUE(company_id, email).

**user_project_scopes** — user_id → users, project_id → projects. PK(user_id, project_id).

**password_history** — user_type enum(STAFF, CUSTOMER), subject_id uuid, password_hash, created_at. INDEX(subject_id, created_at desc).

**refresh_tokens** — company_id, subject_type enum(STAFF, CUSTOMER), subject_id uuid, family_id uuid, family_started_at timestamptz NOT NULL DEFAULT now() (when the family's first token was issued, copied to every rotation: the absolute session lifetime never extends; backfilled with the family's earliest created_at in committed batches of 2,000 families by src/sql/online/0005_indexes.sql), token_hash text UNIQUE, expires_at, revoked_at, revoke_reason, replaced_by_id uuid, user_agent, ip, created_at, last_used_at. INDEX(subject_type, subject_id), INDEX(family_id).

**login_events** — company_id, subject_type, identifier text, success boolean, reason text, ip, user_agent, created_at. INDEX(created_at desc), INDEX(identifier).

**audit_logs** — company_id, actor_type enum(STAFF, CUSTOMER, SYSTEM), actor_id uuid, actor_name text, action text, entity_type text, entity_id uuid, before jsonb, after jsonb, ip, request_id, created_at. INDEX(entity_type, entity_id, created_at desc), INDEX(actor_id, created_at desc), INDEX(created_at desc). **Trigger `audit_logs_immutable` raises on UPDATE/DELETE.**

**audit_seals** (migration 0005) — id bigserial, company_id NULL (NULL = a seal over every company's rows), first_audit_id, last_audit_id, row_count int CHECK > 0, prev_hash text, hash text, sealed_at. A hash chain over audit_logs: each seal covers a run of audit rows in (created_at, id) order and hashes them together with the previous seal's hash, so a changed, removed or inserted audit row breaks every later seal. Append-only (triggers `audit_seals_immutable` / `audit_seals_no_truncate`); kept by reseed. INDEX(company_id, sealed_at desc).

**idempotency_keys** — scope_key text (subject id or ip), key text, method, path, request_hash text, status_code int, response_body jsonb, committed_at timestamptz NULL (the handler's transaction committed: the key is never released for re-execution), lease_expires_at timestamptz NULL (an IN_PROGRESS claim is owned until then; the running request extends it), created_at, expires_at. UNIQUE(scope_key, key). INDEX(expires_at).

**sequences** — company_id, scope text, fy text, value bigint DEFAULT 0. PK(company_id, scope, fy). Increment with `INSERT … ON CONFLICT DO UPDATE SET value = sequences.value + 1 RETURNING value` (atomic).

**job_runs** — job_name, started_at, finished_at, status enum(RUNNING, OK, FAILED, ABANDONED), result jsonb, error text, heartbeat_at timestamptz NULL (liveness beat of the worker running it), checkpoint jsonb NULL (resume point of a heavy job interrupted by a deploy) — the last two since migration 0005. ABANDONED (migration 0003) is set by the `JOB_RUN_SWEEP` job on a row still RUNNING after twice its job's time budget (the worker running it died); a run that finishes later overwrites it with its real outcome.

Raised by the dues engine (DAILY_DUES 00:30 IST, DUES_CATCHUP at boot, POST /dues/run, stage completion): the scheduled runs take one
short transaction per ACTIVE booking — booking locked first, then the booking and its tower's stages read — and the partial unique index
makes a re-run raise only what is missing. A booking whose own data makes the engine throw is isolated (rolled back, logged, counted in
`kkt_dues_booking_failures_total{code}`, listed in the run's `failures` with a message safe to show — raw database text only in the log)
and the run goes on; a transient failure (lock / statement timeout, exhausted serialization retries) is isolated too but makes the job
attempt fail after the run so BullMQ retries it; a database outage (connection lost / refused, server shutting down) stops the run at
once (job retried, POST /dues/run → 503). Super Admins get one bell per finished run (or last attempt) listing the failed bookings.

- **Live path:** every money event appends one row at the end of the current epoch (demand, payment, reversal, agreement change, plan change, other-charge demand/payment/reversal, cancellation). **A voided demand never vanishes:** stage undo, plan change and integrity repair append a `DEMAND_VOIDED` row (amount = −(cash + account) the demand carried, ref_id/ref_number = the demand) after its `DEMAND` row; an earlier advance it absorbed returns to credit.
- **Rebuild = restatement, never rewrite:** `rebuild()` derives the canonical rows from the source tables (voided demands included, with their DEMAND_VOIDED at `voided_at`; a void dated after a cancellation is not a ledger event — a closed book stays as it was closed) and compares them with the current epoch row by row. An identical result writes nothing (agreement revision, plan change and stage undo normally end here: their rows were appended live). A differing one is written as epoch n + 1 (seq from 1), epoch n is closed by a `LEDGER_RESTATED` row (amount 0, its last balances carried, ref_id = the ledger_rebuilds row, note = reason) and a `ledger_rebuilds` row records why. Reasons: AGREEMENT_REVISION, PLAN_CHANGE, STAGE_UNDO, CONSTRUCTION_CHARGE (an on-possession charge un-demanded by a possession undo — the one routine restatement), INTEGRITY_REPAIR, ADMIN_RECOMPUTE, LEDGER_REBUILD.
- **Readers use the current epoch** (`epoch = bookings.ledger_epoch`; helper `epochRows()` / `ledgerRows()`): GET /bookings/:id/ledger (`?epoch=n` reads an older one), summaries, integrity finding (e), reports (statement), payment replay. GET /bookings/:id/ledger/rebuilds lists the restatements.
- **Canonical order = posting order:** `seq` follows the posting instant `at` (then event kind — DEMAND, OTHER_CHARGE_DEMAND, AGREEMENT_CHANGE, PLAN_CHANGE, DEMAND_VOIDED, PAYMENT, OTHER_CHARGE_PAYMENT, REVERSAL, OTHER_CHARGE_REVERSAL, CANCELLATION — then source id); `entry_date` (e.g. a payment's payment_date) is a display attribute only, so a rebuild reproduces the stored seq and running balances, and integrity finding (e) compares the current epoch with a rebuild row by row — each booking on one REPEATABLE READ, READ ONLY snapshot, so a payment committing during the check cannot fake a mismatch. Ledgers written by older versions (business-date order, or voided demands without DEMAND_VOIDED rows) are restated by the admin job `LEDGER_REBUILD` (only ledgers that differ, in batches, audited as `booking.ledger_rebuilt`, reason LEDGER_REBUILD; its result lists the bookings whose row order changed and the bookings that failed, with `failed_count`; a failed booking is logged and the run goes on, while a database outage stops the run so the job is retried); the demo seed ends with it.

## H. Invariants enforced in the database

1. `audit_logs` immutable (trigger).
2. One ACTIVE booking per flat (partial unique).
3. One non-void demand per (booking, installment_seq) (partial unique) — double raising is impossible even under concurrency.
4. One ACTIVE rate card per project; one default bank account; one possession stage per company (partial uniques).
5. `payments.amount_paise > 0`; `site_visits.visitors BETWEEN 1 AND 6`; `service_requests.rating BETWEEN 1 AND 5`.
6. Every business-key uniqueness is scoped by `company_id`.
7. Money splits add up (migration 0002): bookings cash + account agreed = agreement value; demands cash + account = total; other charges total = amount + GST; none of these, demand `paid_paise`, flat/parking prices or rate per sq ft is negative.
8. One live customer per (company, phone) and per (company, PAN hash) — erased rows excluded, exactly as `assertNoDuplicate` checks; one payment per (company, idempotency key).
9. Migration 0005: one ledger `seq` per (booking, epoch); cancellation refund/deduction ≥ 0; ledger epochs ≥ 1; company slugs are unique lowercase kebab; audit_seals is append-only like audit_logs.
10. Privileges (`packages/db/src/sql/0002_privileges.sql`, `infra/postgres/init/01-roles.sql`): the application role `kkt_app` has no UPDATE, DELETE or TRUNCATE on ledger_entries, audit_logs, audit_seals and ledger_rebuilds, and no DELETE or TRUNCATE on payments and demands (it keeps full DML elsewhere, never TRUNCATE, REFERENCES or TRIGGER). The same revokes are applied to the partitions of partitioned tables. Reseed and the test helpers truncate as the owner.
11. Database errors reach clients as envelopes, never 500 (`apps/api/src/lib/pgErrors.ts`): a CHECK violation is 422 `CONSTRAINT_VIOLATION` with `details.constraint` and a readable message (`CONSTRAINT_MESSAGES` covers every CHECK of the schema — tested), a missing reference 422 `CONSTRAINT_VIOLATION` (`details.kind = "foreign_key"`), deleting or re-keying a referenced row 409 `IN_USE` (`details.referenced_by`, `usage_count` — counted through the FK index, capped at 10,000), an untranslated unique violation 409 `DUPLICATE`, a class-22 data exception 400 `VALIDATION_ERROR`. Flats are only referenced by bookings: regenerating or structurally editing a block keeps every flat with booking history IN PLACE (same id, re-snapshotted) when the new layout has the same number on the same floor and position, and answers 409 `FLAT_HAS_BOOKING_HISTORY` listing them when it would delete them (no 500, no IN_USE from the FK).
12. Money guards (`packages/db/src/sql/0006_money_guards.sql`, every role including the owner): ledger_entries and ledger_rebuilds refuse UPDATE and DELETE, and TRUNCATE unless `bookings` is truncated in the same statement (a full reset); a payment's financial columns never change after the insert and its status only moves PENDING → CLEARED | BOUNCED or CLEARED → REVERSED. Violations raise SQLSTATE 23001 (restrict_violation).

## J. Writing migrations (online schema changes)

`pnpm --filter @kkt/db migrate` (`packages/db/src/migrate.ts`) runs, under the migration advisory lock:

1. the drizzle-kit journal (`packages/db/drizzle/*.sql`, one transaction);
2. the hand-written files `packages/db/src/sql/*.sql` (functions, triggers, privileges) — each re-applied only when its sha256 differs from
   the one recorded in `drizzle.kkt_schema_files` or a new drizzle migration was applied since (new tables may need their triggers);
3. the online files `packages/db/src/sql/online/*.sql` — each statement on its own, outside any transaction, re-applied only when the
   file's sha256 changed. Before a `CREATE INDEX CONCURRENTLY` the runner drops an INVALID index of the same name left by an
   interrupted build. On a partitioned table (packages/db/partitions) it builds the index the online way PostgreSQL prescribes: the
   parent index `ON ONLY` the parent (catalog only), then per partition `CREATE INDEX CONCURRENTLY` + `ALTER INDEX … ATTACH PARTITION`
   (resumable: attached partitions are kept, an INVALID partition index is rebuilt); a UNIQUE one is skipped there.

A file is recorded only after it succeeded, so an interrupted deploy re-runs it. `KKT_MIGRATE_REAPPLY_SQL=true` re-applies every file.
Waiting replicas poll the advisory lock (`pg_try_advisory_lock`) instead of blocking inside a statement, which would hold a snapshot that
`CREATE INDEX CONCURRENTLY` waits for.

**Lock timeouts.** Every blocking DDL step runs under `lock_timeout` (`MigrateOptions.lockTimeoutMs`, default 5 s) and is retried with
backoff on 55P03 (`lockRetries`, default 8: 0.5 s, 1 s, 2 s … capped at 30 s): the drizzle journal (one transaction, so a retry starts
clean), each `src/sql` file (one implicit transaction) and each non-CONCURRENTLY online statement. Without it an `ALTER TABLE` queued
behind one long transaction would block every later reader and writer of that table until it got its lock (the migrate role
`kkt_owner` has `lock_timeout = 0` as a role default). `CREATE`/`DROP INDEX CONCURRENTLY` run with no lock timeout: their waits block
nobody. A deploy whose lock never comes free fails with the 55P03 error after the retries; re-run it when the long transaction is gone.

Rules for every new migration (expand → migrate → contract; the previous release keeps running during a rolling deploy):

- **Generate, then edit.** Change the Drizzle schema, run `pnpm --filter @kkt/db generate`, then edit the generated SQL so that each
  statement is cheap on a large table. Commit the snapshot unchanged (it records the end state); `drizzle-kit generate` must then report
  "No schema changes".
- **Indexes on existing tables are built CONCURRENTLY** in `src/sql/online/<NNNN>_<name>.sql`
  (`CREATE INDEX CONCURRENTLY IF NOT EXISTS …`), never in the drizzle migration. Declare them in the Drizzle schema too (so the snapshot
  knows them) and delete their `CREATE INDEX` lines from the generated SQL. A new UNIQUE constraint on an existing table: build the unique
  index concurrently, then `ALTER TABLE … ADD CONSTRAINT … UNIQUE USING INDEX …` in a DO block that checks the catalog first. Indexes of
  tables created in the same migration stay in the migration (the table is empty).
- **CHECK and FOREIGN KEY constraints on existing tables are added `NOT VALID`** in the migration and validated with
  `ALTER TABLE … VALIDATE CONSTRAINT …` in the online file (VALIDATE takes SHARE UPDATE EXCLUSIVE: reads and writes continue).
- **NOT NULL on an existing large column:** add `CHECK (col IS NOT NULL) NOT VALID`, validate it, then `SET NOT NULL` (PostgreSQL uses the
  validated check and skips the scan) and drop the check in a later release.
- **No column type rewrites** (`ALTER COLUMN … TYPE` that rewrites the table, e.g. int → bigint, text → enum). Add a new column, backfill
  it in batches, switch the code, drop the old column one release later.
- **New columns** are nullable or have a constant default (instant in PostgreSQL ≥ 11). Backfills that touch more than a few thousand rows
  run in batches outside the migration (a job or a script), not as one UPDATE.
- **Never drop or rename** a column, table or enum value that the running release still reads; enum values are only added
  (`ALTER TYPE … ADD VALUE IF NOT EXISTS`).
- **Every FK column gets an index** leading on it (the online test fails otherwise).
- **Triggers** live in `src/sql/*.sql` and are created only when missing (`kkt_ensure_trigger`); functions are `CREATE OR REPLACE`. To
  change a trigger's definition, drop it explicitly in the same change. Never DROP + CREATE triggers on every run (each takes an ACCESS
  EXCLUSIVE lock on its table).
- **Online statements are idempotent** (IF NOT EXISTS, catalog-checking DO blocks): an interrupted file is re-run from the top.
- **Re-runs take no blocking lock.** `ALTER TABLE … IF [NOT] EXISTS`, `DROP … IF EXISTS` and a plain `CREATE INDEX IF NOT EXISTS` take
  their table lock BEFORE they look at the catalog, so each re-run would queue behind open transactions (ACCESS EXCLUSIVE even blocks
  reads). Guard every such statement in `src/sql/*.sql` and the online files with a catalog check (`to_regclass(…) IS NULL`,
  `pg_constraint` / `pg_trigger` lookups) inside a DO block; only `CREATE INDEX CONCURRENTLY IF NOT EXISTS` and `VALIDATE CONSTRAINT`
  (SHARE UPDATE EXCLUSIVE) may run unguarded. packages/db/test/online.test.ts re-applies the trigger and online files while a writer
  holds the busiest tables, under a short lock timeout and no retries.
