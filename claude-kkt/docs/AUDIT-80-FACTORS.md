# KKT (existing repository) — 80-factor audit, 1,000 points per factor

Audited: `abhishekpushp07-debug/Kktrealestate` @ `1bcc6ed` (FastAPI + MongoDB backend, CRA React ERP, CRA site, Expo portal). Method: 8 independent scorers (10 factors each) read the code, tests, load-test CSVs and PRD; 8 adversarial second auditors re-read every cited file and could raise or lower each score. All 80 factors were scored; evidence is file:line in the old repository.

## Verdict

**Total: 43,130 / 80,000 (53.9%).** First-pass total was 44,900; the adversarial pass moved it by -1770.

**Is it the world's best? No.** It is a capable, feature-broad prototype (≈ 53.9% of a world-class bar) with real strengths in feature coverage and business-rule awareness, but it is not production-grade for a builder's money: the ledger engine, atomicity, performance, scalability and test rigour score far below the bar, and the measured load test (p50 1.1 s, p95 2.8 s at 1,000 users; payments p95 5.4 s) misses the <300 ms target by 4–9×. The detailed reasons are below; the rebuild in this repository (KKT v2) is designed to close every gap listed.

## Top findings the owner must know (from the adversarial pass)

- **[A]** Bucket cap and idempotency are both check-then-act races on the money path: backend/routers/payments.py:70-78 aggregates paid-so-far then inserts with no conditional write, and backend/infra.py:83-100 does find-then-execute-then-insert with the owner taken from an unverified JWT and failures swallowed; payments.idempotency_key has no unique index (backend/db.py). Two concurrent retries of the same POST /api/payments can both succeed, and concurrent payments can exceed the agreed Cash/Account bucket.
- **[A]** Ledger rebuild is non-atomic and unprotected against concurrency: backend/services/ledger.py:134-136 does delete_many then insert_many on ledger_entries, whose (booking_id, seq) index is not unique (backend/db.py:85). Two payments on one booking, or several uvicorn workers each running reconcile_all at boot (backend/server.py:112 via backend/routers/admin.py:156-164), can interleave and leave duplicate or missing ledger rows that customer statements and receipts then print.
- **[A]** Multi-worker startup is unsafe: every worker's lifespan (backend/server.py:76-116) runs seed_if_empty, seed_phase2/3/5/7/9 and migrate_phase7 behind check-then-act flags (backend/seed.py:22-26, backend/routers/visits.py:522-524), then reconcile_all and integrity_report, and spawns _overdue_loop, _dues_loop and nudge_loop. With WEB_CONCURRENCY=4 (the configuration the PRD load test used) seeds can run concurrently and crash on unique indexes, and overdue/nudge notifications (backend/routers/notifications.py:59-65, backend/routers/visits.py:513-515) are emitted once per worker.
- **[A]** The dues engine can silently never raise an installment: backend/services/dues_engine.py:81,88 skips any installment whose lower-cased name matches an existing demand, but PaymentPlanIn (backend/routers/master.py:150-173) only enforces unique seq, so a plan with two installments of the same name (e.g. two 'Installment' rows) will have its second one skipped forever; the nightly integrity_report flags missing_demand but repair re-runs the same skip. Additionally backend/services/dues_engine.py:104-107 treats any insert exception as a duplicate and drops the demand, and backend/routers/payments.py:146 consumes the FY receipt number before the cap check so rejected payments create numbering gaps.
- **[A]** CPU-bound work runs on the event loop and the Mongo client is untuned: reportlab PDF builds (backend/services/pdf.py:181-183, called from backend/routers/pdfs.py:40,62 and backend/routers/reports.py:76,386,419), bcrypt hashing and verification (backend/routers/auth.py:32-46), the full-database in-memory zip backup (backend/routers/admin.py:85-99) and two BaseHTTPMiddleware layers with body buffering (backend/infra.py:27-101) all block every other request on that worker; backend/db.py:10 creates AsyncIOMotorClient with no pool size or timeouts. Combined with a full ledger rebuild on every payment mutation (backend/routers/payments.py:162,203,215,232), this is why backend/loadtest/out_stats.csv shows p95 2.8 s aggregate and 5.4 s for POST /api/payments against a 300 ms target, and the requirements.txt (157 packages, ~90% unused, including a vendor-URL litellm wheel and both PyJWT and python-jose) widens the attack surface of a service storing PAN/Aadhaar.
- **[B]** Replica-set (transaction) mode is broken for on_booking other charges: backend/routers/bookings.py:184 runs db.bookings.update_one inside the unit_of_work block without uow.kw(), so under a real Mongo transaction the write runs outside the session, cannot see the uncommitted booking insert (bookings.py:178), matches nothing and the on_booking charge is never demanded. The recommended production config (replica set, uow.py:100-107) is untested by every test in backend/tests.
- **[B]** Bucket-cap rule is a read-then-write race: backend/routers/payments.py:70-78 aggregates cleared payments, then :154-156 inserts with no atomic precondition, so two concurrent receipts can push a Cash or Account bucket above the agreed amount; the same pattern lets reverse_payment (payments.py:228-231) apply a second $inc to summary if called twice before rebuild. The booking summary is only corrected later by rebuild().
- **[B]** Ledger materialisation is unsafe under concurrency and runs on every boot of every worker: backend/services/ledger.py:304-306 does delete_many+insert_many outside any session, backend/server.py:112 calls reconcile_all() (admin.py:155-167) for every booking in every uvicorn worker at startup, and backend/db.py:83 has no unique (booking_id, seq) index, so interleaved rebuilds can leave duplicated or empty ledger rows that nothing detects. Also cancel_booking (bookings.py:272) sets demands to 'Cancelled' and rebuild (ledger.py:301-303) immediately resets them to 'Open'.
- **[B]** Payment plans can be corrupted in place: the generic master PATCH model is built by _partial() with __base__=StrictModel (backend/routers/master.py:255-262), which discards PaymentPlanIn's installments validator (master.py:151-173: percents must sum to 100.00, trigger_stage_id required for ON_STAGE, unique seq); _usage_plan is consulted only on deactivate (master.py:436-437). A Super Admin can PATCH a plan used by Active bookings to percents summing to 90% and every new booking will snapshot it via build_snapshot (construction.py:276-279).
- **[B]** Tenant and uniqueness invariants are not enforced by the database: receipt/booking/demand/customer counters are keyed by kind+FY only (backend/services/numbering.py:28, utils.py:153-155), stage and plan names and user emails are globally unique (db.py:21,81-82), customer phone/pan_hash and portal login_phone have no unique index (db.py:62-63; portal.py:625-627 check-then-insert), bank accounts/payment modes/charge types have no usage check before deactivate (master.py:327,363-366), and referenced entities are fetched by id without company_id in bookings.py:119,128-129, payments.py:131,138, construction.py:24,235,303 and documents.py:71,86. Separately, backups never expire because the TTL index (db.py:87) is on an ISO-string expires_at (admin.py:97) and each backup blob is stored inside a Mongo document capped at 16 MB.
- **[C]** Dashboard cache leaks permission-gated data across users: backend/routers/dashboard.py:15 keys the 10 s cache on company_id + project_scope only, while _dashboard (dashboard.py:53-63) adds recent_audit (audit.view), active_users (users.manage), collections (payment.read) and a per-user follow_ups_due list (dashboard.py:92-99 filters assigned_to=user id). Whoever populates the cache first determines what every other same-scope user sees, so a Sales user can be served the Super Admin's audit trail and collections, and one rep's follow-ups can be shown to another. The sibling /dashboard/widgets (dashboard_widgets.py:16) keys on role and user id, so this is an oversight; fix by including role_name/permission hash and user id in the key, or stop caching the per-user parts.
- **[C]** Shipped ERP Flats page and Project > Flats tab are broken by a page-size mismatch: frontend/src/components/common/FlatsTable.jsx:18 requests pageSize: 500 (passed through unchanged by hooks/useList.js:17-19), but backend/utils.py:55 caps page_size at le=200 and backend/tests/test_kkt_erp.py:390-394 plus test_phase_8b.py:30-34 assert that /flats?page_size=500 returns 422. Either raise the cap for /flats, clamp in useList, or change FlatsTable to 200 with paging/virtualisation.
- **[C]** Ledger is fully rebuilt and rewritten on every payment event, outside the transaction, and this is the measured root cause of the latency collapse: backend/services/ledger.py:20-138 reloads all demands and payments, recomputes _oc_totals inside the per-event loop (line 103), updates demands one by one, then delete_many + insert_many all ledger rows (lines 128-131). backend/routers/payments.py:155-162 closes the unit_of_work before calling rebuild(), so even on a replica set the rewrite is non-atomic and GET /bookings/{id}/ledger (bookings.py:215) can observe zero rows mid-rebuild. out_stats_history.csv shows p50 rising 810 -> 1100 ms and p95 1900 -> 2800 ms as 751 payments accumulated on one booking; POST /api/payments p95 is 5.4 s. Append ledger rows incrementally per event inside the uow, or at minimum move the rewrite inside the transaction and paginate payments/ledger in booking detail (bookings.py:206 to_list(500), :215 to_list(1000) silently truncate).
- **[C]** Startup and scheduling are not multi-instance safe, so adding uvicorn workers or pods multiplies work and creates races: backend/server.py:76-115 runs ensure_indexes, five seeders, a roles_version $inc, migrate_phase7, backfill, sweep_notifications, integrity_report, prewarm_variants (thumbs.py:68-86 downloads every media object) and reconcile_all (admin.py:159-167, which calls the delete_many/insert_many rebuild on every booking) in every worker process, then spawns _overdue_loop, _dues_loop and nudge_loop per worker (server.py:99-108) with no leader election or lock. N workers = N nightly dues runs, N SLA sweeps, N concurrent full-ledger rewrites at boot. In-process ttlcache (services/ttlcache.py, invalidated locally in cms.py:105,136,169 and visits.py:275,348,470) and METRICS (infra.py:19) make instances inconsistent. Move seeds/migrations/reconcile to a one-shot job, schedulers to a single worker with a distributed lock or queue, and caches/metrics to Redis/Prometheus.
- **[C]** Every request is a database write and the driver is unconfigured, which is the first thing that will saturate Mongo at scale: deps.py:82-91 enforce_rate_limit is a find_one_and_update upsert executed on every mutating ERP/portal request and, via public_guard (public.py:25-26, a Depends resolved before the memo_public cache wrapper), on every public GET including 20 s cache hits - the marketing site's read traffic becomes primary-node write load. frontend/src/lib/api.js:19 attaches an Idempotency-Key to every POST so infra.py:83-97 adds a find_one, full response-body buffering (and gzip decompress) and an insert_one of the body to every POST. backend/db.py:10 constructs AsyncIOMotorClient with no maxPoolSize, timeouts, compression or read preference. Move rate limits and idempotency to Redis (INCR/EXPIRE, SETNX), exempt cached public reads from the limiter or apply it at the edge, and configure the Motor client explicitly per environment. Also correct docs/part4.md:31, which claims /api/metrics exposes p50/p95 per route while infra.py:104-108 computes only count/avg/max/buckets.
- **[D]** Live credentials persisted in plaintext: the ERP client attaches an Idempotency-Key to every POST (frontend/src/lib/api.js:19) including /api/auth/login and /login/mfa (frontend/src/context/AuthContext.jsx:29,40), and IdempotencyMiddleware stores the full response — raw access_token and raw refresh_token — in db.idempotency_keys for 24 h (backend/infra.py:94-98, TTL at backend/db.py:43). ### A3. Transaction integrity / atomicity — 385/1000

**Strengths.** Flat allocation is genuinely atomic via a preconditioned find_one_and_update (bookings.py:169-171), unique indexes protect receipt/booking numbers and (booking, installment_seq) (db.py:79), counters use atomic $inc, optimistic versioning returns 409 VERSION_CONFLICT with the current document, and the code would use real multi-document transactions if deployed against a replica set.

**Gaps.** On the standalone MongoDB the system actually runs on, there are no ACID guarantees: the money-critical sequence (insert payment, bump summary, rebuild ledger, write audit) is not atomic and partially-applied states are reachable on any failure or crash. Compensations are incomplete for reverse/cancel and run only on in-process exceptions. The bucket cap rule and idempotency are check-then-act races, so double payments and cap overflows are possible under concurrency. Even in transaction mode, generate_number, write_audit and rebuild never receive the session.

**Second auditor.** Verified every cited claim: uow.py:41-55 degrades to ordered writes with compensation only on in-process exception; payments.py:146 consumes the receipt number before _check_cap at :154 and before the insert, so cap failures leave FY numbering gaps; _check_cap (payments.py:70-78) is aggregate-then-insert with no conditional write, so two concurrent payments can both pass; infra.py:83-100 idempotency is find-then-execute-then-insert with except: pass and the payments.idempotency_key field has no unique index (db.py has none), so duplicate payments are possible; reverse_payment registers no compensation; events.py:22-27 swallows audit failures. Additional findings: ledger_entries has only a non-unique (booking_id, seq) index (db.py:85) and rebuild is delete_many then insert_many with no lock, so two concurrent rebuilds of the same booking (two payments, or N workers running reconcile_all at boot) can leave duplicate ledger rows; dues_engine.py:101 consumes a demand number before the insert that may be a duplicate; the IdempotencyMiddleware derives the owner from an unverified JWT (infra.py:76) and replays stored bodies before authentication. Genuine mitigation that the first auditor under-weighted: because summary and ledger are always rebuilt from source documents (single-document inserts) and reconcile_all runs at boot, most partial failures are self-healing rather than permanently corrupting. Net 385.

**World-best would.** Use a database with real transactions (PostgreSQL, or Mongo replica set with every write in the session), enforce caps and idempotency with atomic conditional writes or unique reservations before executing side effects, make ledger derivation append-only or swap-in rather than delete-then-insert, and treat audit as part of the same transaction or a transactional outbox.

Evidence: `backend/uow.py:10-17,41-55 (on standalone Mongo the UoW degrades to ordered writes with best-effort compensation that only runs on an in-process exception; compensation failures are merely logged, uow.py:33-38)`, `backend/routers/payments.py:70-78,147,155-163 (bucket cap is a read-then-insert check, so two concurrent payments can both pass and exceed the agreed bucket; receipt number is consumed before the cap check and insert so failures leave FY numbering gaps; rebuild() runs outside the UoW)`, `backend/infra.py:83-100 (idempotency is find-then-execute-then-insert with except: pass, so concurrent requests with the same Idempotency-Key both execute a payment)`, `backend/routers/payments.py:227-233 and backend/routers/bookings.py:263-272 (reverse_payment registers no compensation at all; cancel_booking compensates only the booking, not flat/parking/demand writes)`, `backend/services/ledger.py:227-230 (rebuild deletes all ledger rows then re-inserts; a crash or concurrent reader between the two sees an empty ledger)`, `backend/events.py:22-27 and backend/utils.py:111-117 (audit write failures are swallowed, so the claim that audit is durable before response does not hold on failure)`

### A7. Background jobs & scheduling robustness — 300/1000

**Strengths.** The dues engine is idempotent thanks to the partial unique index on (booking_id, installment_seq), loops catch exceptions and keep running, the dues job is scheduled at a sensible 00:30 IST, and admin endpoints exist to trigger dues runs and integrity repair manually with audit.

### B1. Data model fit: document store vs relational for a financial ledger — 480/1000

**Strengths.** Money is integer paise and the ledger is an event-sourced projection that can be rebuilt from source documents, which is the right shape for a Mongo-based ledger. A UnitOfWork abstraction exists, and the one constraint that matters most for double-billing (booking, installment) is enforced by a partial unique index.

**Gaps.** The deployment target is a standalone MongoDB, so every multi-document write (flat lock + booking insert + parking + counters) runs without atomicity and relies on best-effort compensation lambdas. Relational-style invariants (sum of demands = order raised, payment.booking exists, bank account referenced by payments) are not expressible in the store and are instead re-checked by a nightly integrity job. Reporting that needs joins (upcoming dues, integrity, customer 360) is implemented as N+1 loops in Python rather than set-based queries. Ledger materialisation is delete_many+insert_many per booking, which neither scales nor is atomic.

**Second auditor.** The first auditor's citations hold (ledger.py:304-306 delete_many+insert_many outside any session; uow.py:100-107 falls back to compensation on standalone Mongo; db.py:79 is the only business-rule index). Two things make it worse than scored. First, the 'recommended' replica-set path is itself broken: bookings.py:184 issues db.bookings.update_one for on_booking other charges inside the unit_of_work block WITHOUT uow.kw(), so under a real transaction the update runs outside the session, cannot see the uncommitted insert (bookings.py:178) and silently matches nothing; the on_booking charge demand is lost. The transaction mode is never exercised by tests (all tests hit a standalone instance). Second, the bucket-cap rule, a core business invariant, is a read-then-write race: _check_cap aggregates cleared payments (payments.py:76,154) and then inserts (payments.py:156) with no atomic guard, so two concurrent receipts can exceed the agreed bucket. Third, cancel_booking sets demands to status 'Cancelled' (bookings.py:272) and then rebuild() immediately overwrites that status back to Open/Partially Paid from FIFO (ledger.py:301-303), so the document model's lack of a single source of truth produces visibly inconsistent state. Mitigations the first auditor under-weighted: the atomic flat lock is a real guarded find_one_and_update and has a concurrency test (test_phase_2.py:89-97), and the owner's 10-row reference ledger is asserted to the rupee (test_ledger_example.py:13-24).

**World-best would.** Put the financial core (bookings, demands, payments, ledger postings) in a relational database with FKs, CHECK constraints, serializable transactions and append-only journal tables, keeping Mongo (if at all) for CMS/content; or at minimum require a replica set so Mongo transactions are always on and model the ledger as immutable postings with materialised balances.

Evidence: `backend/services/ledger.py:20-138 (rebuild(): ledger rows derived from demands/payments/revisions and re-materialised per booking)`, `backend/uow.py:10-16,41-54 (transactions only if replica set/mongos; standalone falls back to 'ordered-writes+compensation')`, `backend/db.py:79 (partial unique index demands(booking_id, installment_seq) is the only DB-enforced business constraint)`, `backend/routers/bookings.py:163-167,201-207 (embedded other_charges/agreement_revisions/summary; joins done with asyncio.gather in app code)`, `backend/routers/reports.py:99-106 (collections report via $group on amount_paise; GST via $expr pseudo-join)`, `backend/routers/construction.py:327-329 (upcoming-dues report loops every Active booking and re-fetches block + demands per booking)`

**Gaps.** There is no migration framework, no schema/version registry, no down-migration and no separation between seeds and migrations; everything runs at process start in each uvicorn worker with a non-atomic marker, so concurrent workers can race. **Second auditor.** Verified: the migration is gated by a settings marker read at migrate_phase7.py:34-35 and written at :141-142, with no lock, and it is invoked from the lifespan of every uvicorn worker (server.py:76-98) together with six seed functions, backfill_demand_installments (full scan of bookings+demands each boot, integrity.py:13-30), an integrity report and sweep_notifications. ### B8. Soft delete / audit immutability — 530/1000

**Strengths.** Financial source documents (payments, demands, bookings) are never deleted in normal flows; reversals, bounces and voids are modelled as state with reasons and actors, and the audit trail has no write API. Masters and documents use soft delete with restore and before/after diffs are captured in the audit.

**Gaps.** Audit durability is best-effort: a failed insert is logged and swallowed, there is no hash chain or DB-level append-only protection, and the audit lives in the same writable database as the data. Ledger entries are wiped and re-inserted per booking without a transaction, so a crash or concurrent read mid-rebuild yields an empty or partial ledger. Flats, CMS content, notices and notifications are hard-deleted, and a Super Admin reseed can erase all production data. Audit snapshots retain full PII (customer.create writes present(doc)).

**Second auditor.** Verified: audit rows are written by an in-process subscriber whose exceptions are swallowed (events.py:22-26,33-42), after the mutation and outside any session, so a mutation can commit with no audit row; no router updates or deletes audit_logs; ledger rebuild is delete_many+insert_many with no session (ledger.py:304-306); customer.create audit stores the full presented document including PII (customers.py:222). The reseed endpoint is more destructive than described: it deletes every collection except audit_logs and login_events, including users, roles, companies and settings (admin.py:40-43), behind only a confirm string and a Super Admin role check. Hard deletes confirmed for flats (blocks.py:258,271), CMS items (cms.py:195), notices (support.py:193), site visits (visits.py:273) and notifications (portal_notify.py:32,71,78). Additional risk: because reconcile_all runs per worker at boot (server.py:112), concurrent rebuilds can interleave delete/insert and leave a booking with duplicated or empty ledger rows, and nothing detects that (no unique (booking_id, seq)). Mitigations that stand: payments are never deleted outside compensation, reversal/bounce/void are modelled as state with actor and reason (payments.py:214,226-228, construction.py:177-180), and masters/documents use is_active/deleted_at with restore.

**World-best would.** Make audit an append-only table protected by DB privileges and a hash chain written in the same transaction as the change, treat ledger rows as immutable postings (never rebuild by delete), forbid hard deletes outside explicit archival jobs, and remove destructive reseed endpoints from production builds.

Evidence: `backend/events.py:22-42 (audit written by in-process subscriber; exceptions are swallowed so a mutation can commit with no audit row)`, `backend/routers/audit.py (read-only router; grep finds no audit_logs update/delete anywhere; admin.py:40 reseed preserves audit_logs)`, `backend/services/ledger.py:134-136 (ledger_entries.delete_many then insert_many, outside any UoW/session)`, `backend/routers/payments.py:157,220-235 (payments only deleted by compensation on failure; reversal keeps the row with reversal metadata and receipt_cancelled)`, `backend/routers/blocks.py:258,271 and routers/cms.py:195, routers/support.py:193, services/portal_notify.py:32 (hard deletes of flats, CMS items, notices, unread notifications)`, `backend/utils.py:45-48 and routers/master.py:469-482, documents.py:85-91 (deleted_at/is_active soft delete with restore for masters and documents)`
